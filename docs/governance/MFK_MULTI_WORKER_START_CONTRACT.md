# 多 worker 開工必讀契約

版本：MW-1.0｜2026-10-03｜適用：MFK 同一任務的並行協作

目的：縮短交付時間，避免互踩與重做；並行不保證節省 token。本契約只規範協作，不自動授權開工、合併或部署。Owner 最新明確指示優先；安全要求及既有權限邊界照常遵守。

## 1. 先讀、先認領，再寫入

每位新加入或接手的 worker，先讀 [AGENTS](../../AGENTS.md)、[COMMANDER_CURRENT](../../COMMANDER_CURRENT.md)、[變更控制](../control/MFK_CHANGE_CONTROL.md) 及其當前控制證據，再讀本契約。重新核對 live main、目標分支與現有工作；舊 SHA、舊部署或舊任務不等於現況。衝突先報 `GOVERNANCE_DRIFT`，停受影響部分，不能自行選版本。

開工前回覆下方任務卡，列出任務負責人、實作者、獨立 reviewer、唯一 integrator、允許／禁止路徑、精確 base SHA、契約版本及驗收條件。未回覆已讀與範圍，不開始寫入。

## 2. 共享契約先行，工作區分開

先對齊 schema、API 請求／回應、狀態與錯誤語義，再拆互不重疊的工作。實際業務契約另用任務附件列出 [現有 contracts](../../contracts) 的路徑與版本；未確認欄位或值明寫「待確認」，不得編造為已定案。

每個實作者用獨立 worktree／目錄及分支，從任務卡的 base 建立；不共用可寫 checkout，不改他人工作區。共用檔案指派單一作者。需要改共享契約時，提出小型協調方案：原因、差異、受影響使用方、相容／遷移與測試；由 integrator 協調確認、更新版本並通知相關 worker。不要永久凍結契約，也不要各自改成不相容版本。

## 3. 作者修正，reviewer 審查

worker 先跑改動範圍的測試、型別／建置及受影響介面檢查，再交精確 commit 和結果。writer ≠ reviewer；reviewer 只讀，回報檔案／位置、影響、重現與優先級，不直接修碼或推送。作者修正後，reviewer 重查新 SHA。

同一授權目標與路徑內，可直接修可重現的小錯並重測，不逐步請示。跨路徑、共享語義、權限、資料破壞或新成本則停相關動作，快速回報具體阻塞與需決定事項；其餘獨立工作可繼續。

## 4. 單一整合，再驗證整體

只有 integrator 整合已審候選到指定整合分支，處理衝突後重跑受影響測試及跨端 smoke，記錄最終合併結果的精確 SHA。各分支各自通過不能代替整合 QA。

同一部署目標同一時間只准一位 publisher；部署前確認目標、現行版本、待發布 SHA 與獨立授權，避免舊 V2／舊分支覆蓋新版本。GitHub 文件、Draft PR、CI 綠燈均不授權 merge、deploy 或 OTA；採用當次已批准的發布路徑；若 Owner 已批准重建舊命令或分支綁定，按該範圍執行，不把舊流程視為永久限制。

三端可按授權並行，先交第一個可用端給 Owner 做 UI 驗收，再逐端交付，不必等全齊。本輪業務資料均為測試資料；驗收前暫不做 Admin／staff 的 UI 登入，但不得因此放寬後端／公開業務 API 安全。現有 Cloudflare 憑證保留，不自行撤銷、輪替或重新綁定。

## 5. 精簡人手、清楚交接

依獨立性、Owner 當次人數上限及 token 預算配置；通常 2–4 位已足夠，有較低上限就遵守，不自動大量開 worker。先定可用時間／token 預算；接近預算或反覆重試無新證據便回報並縮小工作，避免多人重跑同一全量測試。有人詢問先簡短回覆已知結果，重要阻塞即報。

狀態分開報：程式已寫、測試已過、已部署、UI 已驗收；附各自 SHA、命令／證據、未跑項與阻塞，不能以「完成」混稱。API 診斷保留狀態碼、錯誤碼及必要上下文；憑證遮罩，不把有用錯誤整段丟棄，也不把秘密寫入 repo 或訊息。

收到停止／接手指示即停寫入與發布，不自動恢復舊管線。交接列出最後 commit、未提交檔案、測試、仍在跑的工作、下一步與待決定事項；接手者重新核對現況並回覆已讀才續工。

